# QQ 邮件机器人

使用 Python 3.12 标准库，通过 `smtp.qq.com:465` 的 SMTP SSL 发送中文 UTF-8 邮件。
保留原工作流的环境测试步骤；不需要安装第三方依赖。
邮件正文末尾附加实际组装完成时的写信时间，使用北京时间 UTC+8，包含年月日、时分秒。
这个时间与 SMTP 接受、最终投递时间不同；时间后缀不参与正文去重，不能让旧文案因换时间再次发送。

## 每个人独立使用，互相隔离

私有仓库提供完整发送、随机计划和状态功能，也是个人运行数据互相隔离的推荐方式。
暂不迁移时，公开仓库允许仓库所有者手动运行 **QQ Mail Bot（手动发送邮件）**、**小龙娘来信** 与 **邮件状态与历史**。
原始触发者和重跑触发者都必须是仓库所有者；其他触发会显示 `Skipped`。
公开仓库仍不运行随机计划，也不会自动发布状态报告。新发送摘要不保存邮件主题和正文，
但公开仓库的运行元数据、状态分支以及手动查询报告仍可能被其他人查看，不能承诺个人记录保密。
这不是共享多用户服务；每个人都需要自己拥有一个私有运行仓库。

推荐由代码仓库所有者在 **Settings → General → Template repository** 勾选模板选项。
使用者随后点击 **Use this template → Create a new repository**，选择自己的账号和 **Private**，
不要勾选 **Include all branches**。只复制代码，不复制作者的 `mail-bot-state`、旧计划或已用文案账本。
模板功能未启用时，可通过 **Code → Download ZIP** 下载默认分支代码，解压后提交到自己的新私有仓库。
不要 Fork 公开仓库后尝试改私有；公开 fork 通常不能变更为私有。

在自己的私有仓库配置下面三个 Secrets，然后手动发送测试邮件。别人使用时也填写自己的配置，
不要共享仓库的协作权限、授权码或控制令牌。状态分支会在首次需要时自动创建。
本地控制命令必须传 `--repo 你的用户名/你的私有仓库`；Actions 内默认当前仓库，不默认操作原作者。
只有保持私有并限制仓库读取权限，个人日志、计划和新历史才与其他普通使用者隔离；
GitHub、邮件服务及你主动授权的协作者仍可能访问相应数据。

已有使用者迁移时：私有仓库先只放代码，再由自己将旧 `mail-bot-state` 分支完整迁入，
保留去重账本和历史，先检查计划已关闭，再配置 Secrets。不要复制别人的状态或清空自己的账本。
复制代码不会复制 GitHub Secrets、Actions 运行记录或仓库变量，需要单独配置。
已经公开的旧历史不会因迁移消失；清理旧运行记录或重写历史应单独确认处理。

### 隔离是否生效

- 私有仓库的 Secrets、Actions、状态分支均属于自己的仓库。
- 普通其他使用者没有你私有仓库的读取权限；你也没有他们私有仓库的读取权限。
- 公开副本允许所有者手动发送/查询；非所有者的公开副本运行与随机计划仍为 `Skipped`，离线检查仍运行。
- 公开源码和图片不是隐私数据，不要把私人照片或凭据上传到公开副本。

## GitHub Actions Secrets

在仓库 **Settings → Secrets and variables → Actions → New repository secret** 创建：

| Secret 名称 | 内容 |
| --- | --- |
| `QQ_EMAIL` | 启用 SMTP 的完整 QQ 邮箱地址，例如你的 `数字@qq.com` 地址；仅填写邮箱地址 |
| `QQ_SMTP_AUTH_CODE` | 该 QQ 邮箱生成的 SMTP 授权码，**不是 QQ 登录密码** |
| `MAIL_TO` | 一个完整的收件邮箱地址；仅填写邮箱地址，不包含显示名称 |

在 QQ 邮箱设置的账号/安全相关页面启用 POP3/SMTP 或 IMAP/SMTP 服务，按提示生成授权码。
授权码仅填入 Secrets；不要提交 `.env`、凭据文件，也不要在手动触发参数中输入敏感信息。

## 手动发送

将本次代码修改提交并推送到 GitHub 默认分支后：

1. 打开仓库 **Actions → QQ Mail Bot（手动发送邮件） → Run workflow**。
2. 选择默认分支，`message_type` 选择 `test`，`send_delay` 选择 `立即发送`，点击 **Run workflow**。
3. 查看 `Send mail through QQ SMTP` 步骤；成功表示 SMTP 已接受邮件，再检查收件箱和垃圾邮件文件夹。
4. 选择 `random` 可发送一封随机中文长信，发送前会持久预留文案，防止再次使用。
5. 选择 `custom` 并填写 `custom_body` 可发送指定文字；`custom_subject` 留空使用默认主题。
   自定义正文不会消耗随机文案编号。输入是 GitHub 的普通触发参数，不是 Secret，
   即便日志遮罩也不能保证触发参数保密；请勿填写隐私、邮箱授权码或其他凭据。

## 小龙娘来信与文案去重

进入 **Actions → 小龙娘来信 → Run workflow** 可单独发送一封长信。
来信、手动随机邮件和随机计划共用持久文案账本，各发送入口独立排队，以免定时检查挤掉手动任务。
预留记录通过 SHA 校验及有限冲突重试保护；新来信也会进入统一状态与历史，
助手的取消入口可以取消它正在运行的任务。

文案由仓库素材组合生成，不调用外部 AI 服务。编号在尝试 SMTP 前预留，发送失败或结果不确定时也不会再次使用。
旧版已用编号会自动迁移为稳定的文案标识和正文摘要，增加素材不会改变旧记录的含义；不在状态分支保存正文。
第一次使用时会自动创建状态分支，无需先设置随机计划。所有可用组合都已使用时会停止发送，需补充素材。
预留冲突最多进行有限次重新读取和写入；SMTP 发送不自动重试。

预留正文继续在 Actions 日志中遮罩。新长信运行摘要只显示发送结果、实际时间和附件数量，正文在邮箱中查看。

公开仓库的素材、状态分支和 Git 历史均可被读取。去重账本的正文摘要是哈希，
并非加密；读者可枚举公开素材匹配到预留文案。预留不等于发送成功。
账本与旧编号继续保留以防重复发送，不应将它用于保存私人文案。
上传到公开仓库的图片也会公开，请先检查图片内容与照片元数据。

## 图片附件

支持随文字邮件发送一张 PNG、JPEG、GIF 或 WebP 图片，单张图片最大 5 MiB，中文文件名也可使用。

1. 在仓库 **Code → images** 目录选择 **Add file → Upload files**，上传图片并提交到默认分支。
2. 在 **QQ Mail Bot（手动发送邮件） → Run workflow** 中将 `image_path` 填为仓库内的路径，例如 `images/风景.png`。
3. 按需选择邮件类型和发送时机，运行后即可在邮件附件中查看或下载图片。

`image_path` 留空保持纯文字邮件。图片必须位于 `images/` 内，文件内容必须对应支持的图片格式。
路径或文件有问题时会在连接 SMTP 前报错，不会发送部分邮件；无需增加 Secrets。

失败时工作流退出为失败状态，并输出脱敏的配置、认证、TLS、收件人或网络错误说明。
程序不打印底层异常、邮箱地址或授权码，也不开启 SMTP 调试日志。
网络中断可能发生在服务器已接受邮件之后；重跑前先查收件箱，避免重复发送。
程序不自动重试，SMTP 接受邮件也不保证最终投递成功。

## 几分钟后的测试邮件

在 **QQ Mail Bot（手动发送邮件） → Run workflow** 中，将 `message_type` 选为 `random`，
`send_delay` 选为 `3 分钟内随机发送`。工作流完成离线检查后，随机等待 1–180 秒再发送一次。
`Wait before sending` 日志会显示等待秒数和预计开始发送的北京时间，不包含邮箱或授权码。

这是运行器内部的倒计时，触发事件仍为 `workflow_dispatch`，不算 GitHub cron 定时验证。
倒计时从等待步骤开始，GitHub 排队和环境准备时间额外计算，不能保证点击后 5 分钟内收到。
任务总超时为 10 分钟；等待步骤失败会阻止后续发送。默认仍然立即发送。
提交代码只运行不发邮件的检查，不会自动发送测试消息。

## 自定义长期随机计划

**Random Mail Scheduler（随机定时发送）** 支持在自定义范围内随机安排未来发送，最短可为 1 分钟，最长为 90 天。
最短和最长间隔可分别选择分钟、小时或天；每个整数分钟等概率选择。
计划保存到独立的 `mail-bot-state` 分支，运行器和云环境关闭后仍会保留；不需要常驻服务器。
计划默认未启用。定时检查到期后发送一条随机文字消息，图片仍可通过手动邮件工作流发送。

1. 进入 **Actions → Random Mail Scheduler（随机定时发送）**，若已停用，先点击 **Enable workflow**。
2. 点击 **Run workflow**，计划操作选择 **安排一次** 或 **循环随机发送**。
3. 填写 `min_interval` 和 `min_unit`，以及 `max_interval` 和 `max_unit`。
   例如最短 `5` 分钟、最长 `30` 天；或最短 `1` 天、最长 `90` 天。
4. 运行后，未来时间会被保存，本次设置操作不会立即发邮件。下一次具体时间可在状态页面查看。
5. 要取消，运行相同工作流并选择 **关闭计划**。要重设范围，重新选择安排一次或循环随机发送。

单次发送完成后结束邮件计划，保留工作流按配置频率记录后台检查；循环模式每次发送成功后重新随机安排下一次。
发生失败、取消、
连接中断或结果保存失败时会暂停，不会自动重发。先核对收件箱和运行记录，再显式创建新计划。
在 Actions 选择 **关闭计划** 或通过助手关闭，都会保存关闭状态并停用工作流，停止后续后台检查，保留历史。
手动重跑一个已经成功发送的邮件任务会再次发送，因此不能用重跑来刷新状态。

默认每小时约检查一次，几分钟后的目标时间可能要等到下一次检查。
需要更快检查时，在 **Settings → Secrets and variables → Actions → Variables** 创建非敏感变量
`MAIL_BOT_POLL_MINUTES`，值填 `5`；未设置或填 `60` 则每小时检查。
每 5 分钟检查约为每 30 天 8640 次任务，每小时约为 720 次，私有仓库会消耗 Actions 额度。
启动审计在同一个检查任务内完成，受相同频率控制，不单独启动运行器。每次实际后台检查都生成
`startup-audit` 运行摘要及 JSON 文件，可在对应运行的 Artifacts 下载；文件保留 14 天。
记录时间是审计步骤实际执行时间，GitHub 排队和环境启动时间额外计算。完成或暂停计划后审计仍可继续，
要停止全部后台检查需选择 **关闭计划**。未选中的另一条 cron 不启动检查运行器，也不生成启动审计。
GitHub 可能延迟或跳过调度，两种模式都不能保证准点，SMTP 接受也不保证最终投递。
公开仓库长期无活动可能被 GitHub 自动停用定时工作流，跨数月的计划需定期查看状态。
不需要创建新的个人 Token；工作流使用 GitHub 自带的令牌，并仅将邮箱 Secrets 传给发送步骤。

## GPT/助手控制入口

提供 `python -m scripts.control_bot` 作为统一控制入口，供具有终端工具和 GitHub 授权的助手使用。
在本仓库根目录运行，默认查询状态，不发送邮件。复用执行环境已有的 `GH_TOKEN` 或 `GITHUB_TOKEN` 绑定，
不需要把 QQ 邮箱授权码交给 GPT；QQ 凭据继续仅由 Actions 发送步骤读取。
控制操作需要当前 GitHub 授权允许对应的仓库内容及 Actions 读写操作；API 返回 403 时不能认定操作已完成。
工作流已停用时，关闭入口不会重复调用停用 API；若需要保存计划状态，仍需仓库内容写入权限。

| 需求 | 命令示例 |
| --- | --- |
| 查询当前状态和历史 | `python -m scripts.control_bot --repo 你的用户名/你的私有仓库 status` |
| 发送一条随机小消息 | `python -m scripts.control_bot --repo 你的用户名/你的私有仓库 send --type random` |
| 发送指定文字 | `python -m scripts.control_bot --repo 你的用户名/你的私有仓库 send --type custom --body '我在这里'` |
| 随机等待最多 3 分钟再发送 | `python -m scripts.control_bot --repo 你的用户名/你的私有仓库 send --type random --delay random_3min` |
| 发送已上传的图片 | `python -m scripts.control_bot --repo 你的用户名/你的私有仓库 send --image images/photo.jpg` |
| 自定义单次随机计划 | `python -m scripts.control_bot --repo 你的用户名/你的私有仓库 plan --mode once --min 5 --min-unit minutes --max 30 --max-unit days` |
| 自定义循环随机计划 | 同上，将 `--mode once` 改为 `--mode repeat` |
| 关闭自动随机计划 | `python -m scripts.control_bot --repo 你的用户名/你的私有仓库 pause` |
| 取消正在执行的邮件任务 | `python -m scripts.control_bot --repo 你的用户名/你的私有仓库 cancel-run --run-id 运行编号` |

“控制服务器”在这里指触发、停止邮件工作流以及管理计划；GitHub 临时运行器的系统由平台管理。
取消任务不会撤回已经被 SMTP 接受的邮件。命令提交成功后仍要检查 Actions 结果，不能直接当成投递成功。
当前轮询频率及时间范围规则与上文相同；状态查询不会改动已有计划。
若工作流已停用但旧计划仍标记启用，创建新计划会要求先关闭旧计划，防止意外恢复旧目标时间。
关闭操作先停用随机工作流，再保存关闭状态并保留历史；状态发生并发更新时不会强行覆盖或自动重试。
已开始的发送仍可能完成；发送中的旧记录会标为结果不确定，需核对对应运行和收件箱。

GPT/ChatGPT 定时任务需要自己的执行工具和 GitHub 授权。当前控制入口不创建 GPT 定时任务，
也不会向 GPT 任务复制当前会话的凭据；是否能在无人值守的 GPT 任务中调用，需由该任务环境实际提供并验证。
在工具不可用时，GitHub 自身的持久随机计划可独立执行，开启后不依赖此聊天持续在线。

## 当前状态与历史

进入 **Actions → 邮件状态与历史 → Run workflow**，完成后打开这次运行的 **Summary**。
页面会显示两个手动发送工作流的状态、排队/准备/倒计时/发送状态、随机计划是否启用、下次目标时间和最近 20 条记录。
同一次任务的各次重跑分别展示；邮件服务器接受、未发送、失败和结果不确定会分别标明。
也可以在日常发送或计划设置后查看自动生成的状态报告。

该页面是查询时的快照，再次运行状态工作流即可刷新；查看状态不会发送邮件。
正常的定时轮询不会额外启动状态工作流，以减少任务消耗。
所有邮件入口的新摘要仅展示发送结果、实际时间、邮件类型或附件数量，
不保存标题、正文、附件路径、邮箱地址或授权码。自定义正文从触发事件文件读取，
不放入步骤环境变量，并在发送前注册日志遮罩。
点击历史记录可查看对应运行摘要。较早的 QQ Mail Bot（手动发送邮件） 摘要可能保存了完整主题与正文；
修改代码不会清除旧日志和摘要。公开前应检查已有运行记录，含敏感内容的记录需单独处理。
GitHub 的 Actions Secrets 不随公开操作公开，但普通触发参数、日志、摘要和状态记录不能作为私密存储。
GitHub 运行记录删除或过期后，其摘要也无法查看；随机计划状态分支保留最多 100 条发送结果元数据。
如果持久计划标记启用而工作流被停用，报告会明确显示当前无法自动发送，不把它当成正常等待。

## 时间与现实时间

邮件日期、日志和页面统一显示北京时间（UTC+8），计划内部保存带时区的 UTC 时间。
计划以运行器实际执行时的系统时钟为基准，不使用聊天日期或固定示例日期；跨日、跨月、跨年自动换算。
重启不会改动已经保存的目标时间，存储保留小数秒，避免把随机间隔提前截短。

| 时间 | 含义 |
| --- | --- |
| 计划发送时间 | 希望执行的目标时间，GitHub 可能稍后才启动检查 |
| 邮件 Date | 登录 SMTP 后、实际提交邮件前的时间，明确标为 +0800 |
| SMTP 接受时间 | 服务器确认接受后立即记录的时间，不是最终收件时间 |
| 步骤结束/状态记录时间 | GitHub 步骤完成或结果保存的时间，历史表注明来源 |
| 查询开始/完成时间 | 本次状态查询的真实起止时间；打开旧报告不会自动刷新 |

计划过期时页面显示已晚多少分秒。无法确认的旧重跑时间显示“时间未知”，不会借用其他重跑的时间。
新随机发送记录使用发送步骤输出的真实 SMTP 接受时间；旧记录仍按原始状态记录时间显示。
要获取新快照，重新运行“邮件状态与历史”。实际投递时间由收件邮箱决定，不能保证与计划时间完全一致。

## 可选定时发送

GitHub 定时调度可能延迟或跳过，不适合验证严格的几分钟内发送。
当前未启用固定每日发送；未来可以按每日发送需求添加以下配置。

先验证手动发送成功，再在 `.github/workflows/main.yml` 的 `on` 下、与 `workflow_dispatch` 同级加入：

```yaml
  schedule:
    - cron: '17 1 * * *'
```

这会每天北京时间 09:17（UTC 01:17）先预留文案，再发送随机长信；非整点安排有助于避开调度高峰，但仍不保证准点。
GitHub 定时工作流仅运行默认分支，可能延迟或被平台跳过；公开仓库长时间没有活动时，定时任务可能被禁用。

## 本地离线验证

在仓库根目录运行 `python -m unittest discover -s tests -v`。
测试模拟 SMTP、倒计时及 GitHub API，验证 UTF-8 编码、图片附件、持久随机计划、状态历史、失败状态和日志脱敏，不会发送邮件或实际等待。
**Mail Bot Checks（代码检查，不发送邮件）** 工作流会在推送到 `main` 或创建 PR 时运行这些离线测试，不读取邮箱 Secrets。
真实 QQ SMTP 认证与投递需要配置 Secrets 后通过 Actions 测试。
